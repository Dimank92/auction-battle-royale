Профессиональная backend-система для проведения высоконагруженных аукционов в стиле "Battle Royale" (Top-N победителей). Система поддерживает строгую транзакционность, защиту от снайперов и гибкие финансовые настройки.

- **🌐 Живое демо**: [http://localhost:3000](http://localhost:3000)

## 🏆 Что нового в версии v2.0 (Strict Edition):
- **🛡️ Strict Top Bid**: Теперь любая ставка ОБЯЗАНА перебивать текущего лидера. Никаких «скрытых» ставок в середину списка — только борьба за №1.
- **⏱️ Anti-Sniping (Seconds-based)**: Высокоточное управление временем. Настройка окна срабатывания и добавления времени теперь в секундах.
- **💎 Финансовая целостность**: Использование ACID-транзакций MongoDB и статических моделей Mongoose для исключения ошибок при выплатах и возвратах.

## 💡 Анализ механики (Product Engineering)

По результатам анализа Telegram Gift Auctions, в систему заложены следующие продуктовые решения:

1.  **Механика раундов (Battle Royale)**: Аукцион не заканчивается одним победителем. Есть фиксированное количество "мест" (Top-N). Это создает динамику, где пользователи соревнуются за право остаться в списке, а не просто за первое место.
2.  **Экономика ставок**:
    *   **Locking**: Мы блокируем средства сразу при ставке. Это гарантирует, что на момент завершения раунда у победителя точно есть деньги.
    *   **Instant Refund**: Если участника вытесняют из списка победителей более высокой ставкой, его средства разблокируются мгновенно (в той же ACID транзакции), что позволяет ему сразу сделать новую ставку.
3.  **Anti-Sniping (Soft Close)**: Мы отошли от "жесткого" дедлайна. Любая активность в "окне защиты" (1-5 мин) продлевает аукцион. Это максимизирует выручку продавца и делает борьбу честной для тех, у кого медленный интернет.
4.  **Резервная цена**: Механизм защиты продавца. Если интерес к лоту ниже ожидаемого, раунд признается несостоявшимся, и система защищает актив, возвращая средства всем участникам.

## 🚀 Ключевые механизмы

### 1. Bidding & Concurrency (Ставки и конкурентность)
- **ACID Transactions**: Все ставки проходят через сессии MongoDB. Списание баланса (`available -> locked`) и обновление состояния аукциона атомарны.
- **Optimistic Concurrency**: Используется версионирование документов (`__v`). Если два пользователя ставят одновременно, один из них получит ошибку версии и должен будет перечитать состояние (релизовано на уровне БД).
- **Battle Royale Logic**: При заполнении списка участников (например, 1000 мест), новая более высокая ставка вытесняет самую слабую. Вытесненный пользователь получает мгновенный возврат средств.

### 2. Anti-Sniping (Защита от снайперов)
- Если ставка поступает в последние `N` минут (настраивается), время завершения аукциона (`endsAt`) автоматически продлевается. Это дает другим участникам время на реакцию.

### 3. Financial Flow (Финансы)
- **Locking**: Средства блокируются в поле `wallet.locked` при совершении ставки.
- **Settlement**: При завершении раунда `AuctionTicker` проверяет **Reserve Price**.
    - Если порог пройден: Победители теряют `locked` средства, продавец получает выплату за вычетом **комиссии platform fee**.
    - Если порог НЕ пройден: Все средства возвращаются на `available` баланс участников.
- **Audit**: Все выплаты фиксируются в коллекции `Transactions`.

### 4. Auction Ticker
Фоновый процесс, который:
- Переводит аукционы из `PREVIEW` в `ACTIVE`.
- Обрабатывает завершение раундов.
- Автоматически создает следующий раунд, наследуя конфигурацию.

## 🛠 Установка и запуск

1. **Зависимости**: `npm install`
2. **База данных**: `docker-compose up -d` (нужен Docker для Replica Set).
3. **Запуск**: `npm run dev`
4. **Доступ**: [http://localhost:3000](http://localhost:3000)

## 🧪 Верификация
Для проверки всех функций предусмотрены скрипты:
- `npm run test` (если настроен Jest)
- `npx ts-node tests/prod-verify.ts` — полный прогон проверки шага ставки и анти-снайпинга.
- `npx ts-node tests/load-test.ts` — проверка системы под нагрузкой.
